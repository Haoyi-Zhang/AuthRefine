# Stateful requirements and review provenance

Read on 2026-10-24 from official RFC Editor sources:

- RFC 6749, D. Hardt (ed.), 2012, section 4.1.2:
  https://www.rfc-editor.org/rfc/rfc6749.html#section-4.1.2
  A code is single-use and bound to a client identifier and redirection URI.
- RFC 7009, T. Lodderstedt, S. Dronia and M. Scurtescu, 2013, section 2.1:
  https://www.rfc-editor.org/rfc/rfc7009.html#section-2.1
  Revocation invalidates the actual token; propagation to related tokens depends
  on the server policy and grant relationships. Section 2.2 distinguishes the
  revocation endpoint's response from later token-use authorization.

These are normative stateful policies, not merely static public examples. The
finite models and candidate mappings in `src/stateful_review.py` are ours.
The RFCs do not provide unresolved aliases, known implementation bugs, or a
historical review dispute. A model reviewer supplies alternative client/redirect
record mappings or a same-grant token association from incomplete configuration.
The checker identifies exactly which such mappings a candidate table implements.
It does not decide which candidate the issuer intended or should approve.

The code model fixes one unexpired authorization code. The revocation model
fixes one authenticated revocation, an actual token and two candidate related
tokens. The `used` and `revocation_seen` bits must come from an instrumented
token-store/model export, not an allow/deny-only production API. This is the
consumer who can supply the full-state decoder: the service's model exporter
or its verification engineer. The pilot does not implement that export from
a running OAuth service.

The revocation bit records the accepted revoke operation, not a full per-token
validity database. A fixed server policy revokes one related token; the alias
determines its record association. Revocation acceptance is modeled as `allow`
and token-use failure as `deny`; these are not HTTP status codes. Expiry, PKCE,
cryptography, concurrent operations, propagation delay and RFC 6749's recommended
revocation after replay are excluded. Denial stutters, so that latter side effect
would need a different interface or a separately modeled accepted operation.

State-loss mutations, repaired tables and review actions are controlled owned
examples. They are not external maintenance incidents, independent deployment
validation, user studies, or vulnerability reproductions. No network requests
are generated by the experiment. No RFC prose or code component is copied into
the models; the requirements above are paraphrased with attribution.

## Closest new literature

Han Xu, Zachary Kincaid and David Walker, *Network Analysis with Parametric
NetKAT*, arXiv:2607.09637v1, 10 July 2026:
https://arxiv.org/html/2607.09637v1

Read sections 4 (queries/semantics), 5.2 (valuation-preserving set embedding),
and 5.3 (solution-set emptiness and weighted aggregation algorithms), including
their stated output specifications. Parameter valuations remain fixed along
traces; collecting all satisfying valuations is therefore not a novelty of
this artifact. `symbolic_profile.py` is an owned finite-domain-diagram comparator,
not the Parametric NetKAT implementation. The supplied complete source-state map
justifies computing shortest failure ranks from target distances here; no claim
is made that another parametric framework could not express the same question.
